# Deploying on Vercel

The live demo runs as two Vercel projects, with the books in a hosted Postgres and the graph on FalkorDB Cloud:

| Project | What it serves | How it is built |
|---|---|---|
| `munim-cobnut` | `apps/web`, the storefront and staff screens | Vercel's Next.js build, Root Directory `apps/web`, installed from the workspace root with the frozen lockfile |
| `munim-api` | three services: `core` (core-api, plus core-worker's jobs behind a cron route), `intel` (Python, the AI layer), `suppliers` (Python, the simulated suppliers) | staged by `build.mjs` into `deploy/vercel/out/` and uploaded as is |

The web app reaches the API only through its own `/api/*` rewrite (`MUNIM_API_ORIGIN`), so the browser talks to one origin.

## How `munim-api` is put together

`node deploy/vercel/build.mjs [--out <dir>]` stages one self-contained directory ([`vercel.json`](./vercel.json) is its
configuration):

- `core/`: core-api, core-worker, `packages/config`, `packages/contracts`, `packages/core-domain`, the sign-in and storage
  adapters, **and `adapters/falkordb`** with its Cypher files and its client, at their repository paths, with a flat
  `node_modules` (`deploy/vercel/test/build.test.ts` checks the graph adapter is staged without its tests). Its entry,
  `core/index.mjs`, boots core-api through `services/core-api/src/env-root.ts`, which reads its whole configuration from the
  environment.
- `intel/` and `suppliers/`: the two Python services and their requirements, exported from `uv.lock`.
- Routing: `/suppliers-sim/*` goes to `suppliers`, everything else to `core`. `intel` has no public route: core reaches it
  through a service binding (`MUNIM_INTEL_URL`), and every call carries the service secret.
- Cron: `0 1 * * *` calls `GET /internal/cron/v1/tick`, which runs every core-worker job once, `graph-project` included. On
  this schedule the graph is still always current, because every graph read rebuilds it first when the books have changed.

`node deploy/vercel/deploy.mjs [--project munim-api|munim-cobnut|both] [--ref <rev>] [--dry-run]` creates, links and deploys
the projects with a logged-in Vercel CLI; `--dry-run` prints every command and runs none.

## The graph on FalkorDB Cloud

1. Create a FalkorDB Cloud instance and take its `rediss://` URL.
2. Check it allows what the rebuild needs: `MUNIM_FALKORDB_URL=rediss://… node scripts/dev/probe-falkordb.ts` (it builds
   one scratch graph under a staging-shaped key, renames it, and deletes it; exit 0 means every check passed).
3. On `munim-api`, set `MUNIM_GRAPH=falkordb` and `MUNIM_FALKORDB_URL` (a secret: it may carry a password, and config
   redacts it from every log line). Project variables reach all three services; only `core` reads these two (intel has no
   FalkorDB client and reaches the graph through core). On `munim-cobnut`, set `MUNIM_GRAPH=falkordb` for the build and the server: it shows the
   "Supplier map" links and the `/staff/suppliers/map` page.
4. Redeploy both. The graph is built on the first read; nothing needs seeding into FalkorDB.

## Environment variables

Names only; values never belong in the repository. `node deploy/vercel/env-setup.ts` sends the values it can resolve
(from `.env` through `packages/config`, and from files earlier steps write under `.run/`) to both projects, printing names
only; `--dry-run` lists each name with its source. The two graph variables above are set by hand.

| Name | Project | What |
|---|---|---|
| `SUPABASE_TRANSACTION_POOLER_CONNECTION_STRING`, `SUPABASE_SESSION_POOLER_CONNECTION_STRING`, `SUPABASE_PROJECT_ID` | api | where the hosted Postgres is (each role logs in with its own password) |
| `SUPABASE_PROJECT_URL`, `SUPABASE_PUBLISHABLE_KEY` | api, web | the hosted sign-in (the publishable key is public by design) |
| `SUPABASE_SECRET_KEY`, `MUNIM_BLOB`, `MUNIM_BLOB_BUCKET` | api | the uploads bucket |
| `MUNIM_DB_PASSWORD_MUNIM_CORE`, `MUNIM_DB_PASSWORD_MUNIM_SVC`, `MUNIM_DB_PASSWORD_MUNIM_PLATFORM` | api | the runtime roles' passwords (`node db/scripts/bootstrap-roles.ts` writes them to `.run/db-roles.json`) |
| `MUNIM_SERVICE_SECRET`, `MUNIM_RUN_TOKEN_PRIVATE_KEY_PEM`, `MUNIM_RUN_TOKEN_PUBLIC_KEY_PEM`, `CRON_SECRET` | api | generated by `env-setup.ts` |
| `MUNIM_CORE_URL`, `SUPPLIERS_SIM_PUBLIC_URL` | api | the API project's own origin, and `<origin>/suppliers-sim` |
| `MUNIM_MODEL_MODE`, `GEMINI_API_KEY` | api | live models, with the recorded response of the same call as the fallback |
| `MUNIM_GRAPH`, `MUNIM_FALKORDB_URL` | api (both), web (`MUNIM_GRAPH`) | the graph backend |
| `NEXT_PUBLIC_MUNIM_API`, `MUNIM_API_ORIGIN`, `NEXT_PUBLIC_MUNIM_STOREFRONT_KEY`, `MUNIM_DEMO_SIGNIN`, `MUNIM_DEMO_PASSWORD`, `MUNIM_DEMO_TENANT_ID` | web | the `/api` rewrite, the storefront key and the demo sign-in |

## The database

Deploy against a database of its own. With `MUNIM_DB_URL_SESSION` exported as an admin connection string:

```bash
pnpm -F @munim/db migrate              # every migration, in order, one transaction each
pnpm -F @munim/db seed:packs           # the country packs
node db/scripts/bootstrap-roles.ts     # a fresh password per runtime role, into .run/db-roles.json
```

Then seed the demo business through the deployed API with `tools/worldgen` (`node tools/worldgen/src/cli.ts --world=cobnut`;
its README lists the sign-in tokens it needs), whose files under `.run/cobnut/` give the web project its tenant id and
storefront key. The demo people's sign-ins are made by `adapters/dev/idp-supabase/demo-accounts.ts`.
